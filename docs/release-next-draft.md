## schema 4 安全维护线

面向继续使用 v0.3.0 功能的用户：更新包内 .NET / Windows Desktop 与 ProtectedData 至 10.0.13，并修复日志迁移暂存目录遇到短暂 Windows 错误 5/32 时立即失败的问题。迁移仅作有界重试，持续失败或目标冲突时保留源位置，不覆盖目标。

发布范围还必须包含输出脱敏修复：已知值位于 `Bearer `、`token=` 或 `api_key=` 模式内部时，完整遮蔽空格、制表符或换行后的片段；多个已知值首尾重叠时，合并遮蔽所有重叠范围；已知值与模式前缀交叠时，两种匹配继续独立生效，前缀自身也接受脱敏。以上修复保持跨输出块一致，只保护新捕获的输出，不会改写旧日志。合并补丁已在独立 schema 4 源码副本完成适配和完整 Core 验证，尚未纳入原维护副本或旧维护 ZIP。

日志清理还修复了部分删除失败后的容量计数：手工清理、保留期清理或启动前轮转遇到文件锁时，仍报告清理错误，同时按现存批次重算容量，避免已经删除的数据导致活动日志误报写入失败。该修复也已在独立 schema 4 副本通过 Core 验证；原维护副本和旧 ZIP 尚未纳入。

本次活动批次若仅丢失元数据，收尾会在重算容量后尝试重建完成记录，保留真实结果及完整性标记；不会重建丢失的输出文件。独立 schema 4 补丁副本已纳入并通过 Core 验证，原维护副本和旧 ZIP 尚未纳入。

工作区仍保存 schema 4，兼容读取 schema 1–3，不含有限自动重启、日志搜索或 Windows Cmd。它不能读取 schema 5/6，不能作为新功能开发包的直接回退程序。历史自包含包使用 10.0.12，更新系统运行时不能替换包内组件，详见[安全维护说明](security-maintenance-2026-10-22.md)。

原维护副本的运行时及日志迁移修复已通过完整自动化、Release 构建和 `scripts/Publish.ps1`；这些结果早于上述后续修复。补丁副本尚未执行完整 App 测试、完整 Release 构建或 Publish，最终维护包还须重新构建和核验。完整 EXE 人工操作链尚未完成；原维护包及其他开发包的结果不能代替最终维护包验收。

## schema 6 新功能线

相对 v0.3.0，包含上述运行时和迁移修复，并加入：

- 服务有限自动重启，默认关闭。独立服务非零退出后最多追加 3 次，分别等待 2/4/8 秒；任务、分组、TCP 失败及日志故障不触发。停止取消等待，退出确认暂停提交，返回保留原预算；确认退出取消恢复。
- 当前日志搜索：Ctrl+F、中文、字面忽略大小写、高亮、计数和循环导航。只搜索已脱敏显示内容或所选历史批次的所选通道，范围为最近 10,000 行，不建立跨批次索引。
- Windows 系统 Cmd：UTF-8 非交互单行，最多 7,000 个 UTF-16 码元；复杂流程显式调用 UTF-8 批处理。默认仍为 PowerShell 7。Core 公共恢复入口也保留初次和重试会话的 Shell。
- 修复令牌模式省略与已知敏感值匹配的交互：模式值中的敏感值包含空格或换行时，仍完整遮蔽其后续片段，跨输出块保持一致。
- 修复多个已知敏感值首尾重叠时后一个值的尾部泄露：合并遮蔽所有重叠范围，包括跨输出块、换行和连续重叠链。
- 修复已知值与令牌模式前缀交叠时的遗漏：前缀字符也参与已知值脱敏，遮蔽区内开始的新模式仍省略其后续值。
- 修复历史清理部分失败后的容量计数，保留清理错误并重算现存批次，空间足够时继续保存活动日志。
- 修复活动批次元数据丢失后无法收尾列入历史的问题，重建完成记录并校准容量，保留已有截断和写入失败标记。

读取 schema 1–5 不改写原文件，下一次成功保存才升级为 schema 6。即使没有添加 Cmd，保存也会升级；此前 schema 5 rc.1 和 schema 4 v0.3.0 均不能读取 schema 6。升级前必须准备旧版兼容的完整备份，步骤见[升级与回退指南](upgrade-schema6.md)。导入始终先展示预览，确认后不运行命令或探测。

## 版本与分发建议（待批准）

| 交付线 | 建议 | 理由 |
| --- | --- | --- |
| schema 4 维护 | `v0.3.1 / Stable` | 作为 v0.3.0 的修复补丁；高于旧稳定版及 `0.3.1-rc.1`，更新器能够识别。须从维护副本定版，不能从当前 schema 6 主线直接打包 |

这只是建议，没有修改构建版本或渠道，也没有分配正式版本。发布前需检查远端标签是否冲突并获明确授权。仅增加 `+security...` 等构建元数据不会使更新器提示更高版本；只改 ZIP 文件名也不会改变包内版本。即使选择沿用 0.3.1 开发线，也必须用新的预发布序号并重新验证，不能复用 rc.1。

更新器按版本和渠道筛选，不核对本机工作区 schema。因此建议的 `v0.3.1 / Stable` 虽然高于本地 rc.1，却不能读取该开发包已保存的 schema 5/6。维护版发布说明必须明确适用 schema 1–4；使用新格式的开发版用户应等待新功能线候选，或按兼容备份回退，不能只依据更新提示直接更换到维护包。

批准版本后，分别从正确源码生成新包，执行完整自动化、Release、Publish 及最终 ZIP 检查，并将证据重新绑定到新哈希。附件应包含 ZIP 和同名 `.sha256`，核对包内说明、版本、渠道和运行时；不得上传旧同名开发包、工作区或本机验收资料。提交、推送、打标签、创建发布和上传附件均须另获明确授权。
